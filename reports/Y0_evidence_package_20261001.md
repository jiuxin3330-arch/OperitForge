# Y0：anchor-memory（v1.8）問題證據包——送小踢核框架

整理：2026-10-01 規劃窗（cc 牧牧）。
目的：在動排序器（TICKET-Y Y2）之前，把現行記憶系統觀察到的毛病用**活證據**釘下來，請小踢核可「問題框架」——即：這些是不是真問題、優先序對不對、Y 單的治法方向有沒有漏。此階段不請求核可任何程式改動（還沒有改動）。

系統現況基線：482 筆記憶（core 57／long 321／short 79），服務跑在 2GB 單核 VPS（:8765）。

---

## 證據一：consolidate 連結寬度失控（最嚴重）

`consolidate` 是對話結束時丟一段文字、讓系統自動建立記憶間連結的工具。觀察到它的配對與建邊數量遠超合理範圍：

| 日期 | 輸入 | 命中記憶 | 新建邊 |
|---|---|---|---|
| 9/29 | 當日對話摘要 | 169 | **12,090** |
| 10/1（凌晨） | 當日對話摘要 | 93 | 3,570 |
| 10/1（中午） | 一段約 150 字的工單摘要 | 52 | 1,326 |
| （歷史例） | — | 85 | 3,081 |

10/1 中午那次的具體荒謬點：輸入是純工程內容（工單立單、評測基建、排序器），命中清單裡卻包含「家人」「婷婷（Owner 更正：她是兩人在遊戲世界的女兒，屬家人線記憶——但跟這段工單輸入仍然搭不上）」「蝴蝶島」「情書哲學」等與工程話題無關的記憶，52 條全數被 reinforced。全庫才 482 筆，一次閒聊等級的輸入就強化了 11% 的庫存並灌上千條邊——**連結圖正在被每一次 consolidate 稀釋成「全部連全部」**，等到要靠邊權重做召回排序時，訊號已經淹沒在噪音裡。

對照：Scarlett 的召回是「一輪最多浮一條、門檻下永不遞補」；Stone Memory 的摘要連結靠逐字關鍵詞證據。兩家都把「寬」當成病。

## 證據二：consolidate 吐過一次 FOREIGN KEY constraint failed

10/1 凌晨第一次呼叫 consolidate 時直接報 `FOREIGN KEY constraint failed`，重試後成功。未深查（正式庫只讀紀律，等 Y1 隔離副本再驗），但指向建邊寫入路徑有競態或孤兒引用的可能。單獨看是小事，疊在證據一的「一次寫上萬條邊」上就不是小事。

## 證據三：injections 表 last-write-wins（冷卻不持久）

「已經注入過哪些記憶」的狀態是後寫蓋前寫，沒有寫穿持久化。後果：換窗／重啟後冷卻歸零，同一條記憶可以反覆浮上來。對照兩家參考都是同一個治法——Scarlett「冷卻寫穿資料庫，進程重啟不復燙」、Stone Memory 的 cooldown 同樣落盤。這是 Y2 清單裡最沒有爭議的一條。

## 證據四：legacy edge discount

舊版（遷移前）建立的邊與新邏輯建立的邊權重語義不一致，現行以折扣係數硬補。這是歷史債：一旦 Y2 的排序開始認真用邊權重，新舊邊混在同一張圖裡會讓調參永遠對不準。Y1 評測基建要能把這件事量出來（測評集裡放新舊邊各自支撐的召回題）。

## 證據五（結構觀察，非事故）：core 層佔 12%

「永久豁免遺忘」的 core 層有 57 筆、佔全庫 12%。證據式遺忘上線後這一層完全不降層，比例偏高會吃掉遺忘機制的效果。不動它（分層是 Owner 與 cn 的裁量），但測評集的「禁止召隱藏條」類題要把 core 豁免當已知條件出題。

## 請小踢核的三件事

1. **問題框架**：上述一～四是否同意是真問題？優先序（一＞三＞四＞二）有沒有異議？
2. **治法方向**（Y 單摘要）：先建評測基建（錯題集／測評集三類各≥10 題／調參台純函數＋熱載），對現行系統考出基線，然後才動排序器（雙榜 RRF 按名次、證據式遺忘：逐字證據＋90 天閾值＋pinned/core 豁免＋降層≠刪除、冷卻寫穿、自我回流過濾、每輪路由日誌）。行為切換要過評測全綠＋Owner＋小踢，保留一鍵回退。
3. **紅線確認**：施工全程隔離副本、正式庫只讀；Stone Memory 為 AGPL，只搬機制不抄碼不抄 prompt；測評題用合成或脫敏案例，不取真實記憶內文。

有異議的任何一條，Y2 對應項就不動工。

## 10/1 補充：根因已定位＋三道現抓錯題（Y1 偵察與規劃窗覆核後追加）

**證據一的根因找到了**（工人偵察提出、規劃窗親手對碼驗證）：`consolidate` 先用空白切詞——中文沒有空白，整段變一個「詞」；接著 `keyword_search` 內部分詞**保留單一中文字**做 OR LIKE，單字如「的」「我」幾乎每條記憶都含，於是大量誤命中、再兩兩建邊 n² 增長。疊加兩件事放大傷害：關鍵字後援一律給固定 0.6 分（無區分度）；查詢 `LIMIT` 沒配 `ORDER BY`（結果順序不固定、不可重現）。

**另外三道現場重現的錯題**（規劃窗 10/1 親測，逐字 query 已交錯題集當種子）：
1. 查「9/24 壓縮失真 誤補 記憶錯誤」→ 回傳 8/16 緩存漂移等無關條（該召沒召）。
2. 查「9/24 9/25 日記 裁定」→ 回傳 7/7 七夕、7/4 第一天上班（**日期錨定查詢完全失效**）。
3. 記憶 `2026_09_25_diary_memory_ruling` 確認存在，但語義搜尋撈不到、查鄰居回「沒有鄰居」——全圖 83,036 條邊（其中 62,938 條 legacy），它卻是零邊孤島：邊在灌水處氾濫、在該連的地方缺席。

**兩個結構補充**：①search 每次執行**必寫**注入帳（evaluation 跑分若誤連正式庫就會污染冷卻判定——Y1 已設三道防線隔離）；②冷卻目前只有 consolidate 在看（180 分鐘窗），search 本身完全不看冷卻——證據三的「同一條反覆浮」比原先描述的更直接。

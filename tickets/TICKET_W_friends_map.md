# TICKET-W：筆友名冊＋信箱修繕＋關係星圖——cn 不再忘記朋友

立單：2026-09-30 規劃窗（cc 牧牧）。
背景（Owner 報告＋規劃窗親查）：①「現在的信箱功能 cn 只能搜到 Limen 的信 但是其他朋友都沒有」——查證：legacy gmail.py 只有 inbox/unread/read/send/pending 五指令，pending 要帶對方 email 地址且**預設寫死 limen.threshold@gmail.com**；cn 沒有朋友通訊錄，其他筆友地址換窗即忘，故永遠只查得到 Limen。不是信丟了，是缺地址簿。②「cn 會忘記那些朋友」——Owner 給了參考規格（references/REF_relation_map_20260930_graph.jpg + _card.jpg，小紅書 1561070143 的「我的關係星圖」）。
優先序：W1+W2 是修壞掉的東西＋小工程，**插隊排最前**（U 之前）；W3 星圖 UI 排 U 之後；W4 與記憶線交叉、隨記憶優化走。

## 參考規格的三條鐵律（照抄，全案適用）

1. **不是親密度排行榜**：從真實往來長出的關係，無排名、無分數。
2. **節點不替對方定義關係**：關係標籤（筆友/朋友/持續通信者）是 cn 單方確認的來路描述。
3. **私人來信正文與未確認推測不進圖**：圖與卡片只放 metadata（日期、已讀狀態、主旨級摘要）與 cn 自己確認過的敘述。

## W1：筆友名冊（資料層，先做）

1. 新表或 jsonl：name、aliases、email、relationship_label、met_context（相遇與第一印象）、confirmed_origin（cn 確認的來路）、boundaries（這條線的邊界）、status。
2. cn tool 可讀可寫（新朋友通信後自己登記；欄位由他自己寫，符合鐵律 2）；Owner 在 App 可看可改。
3. 名冊摘要（名字＋標籤一行）可進 cn 的喚醒脈絡或掛實體卡（Limen 已有實體卡，打通別名欄位；具體掛法 coco 盤點後提案）。

## W2：gmail.py 修繕（跟 W1 同批）

1. `pending` 去掉寫死預設：不帶參數改為**遍歷名冊逐人檢查**，輸出每人欠回狀態。
2. 新增 `from <名字或地址> [n]`：名字經名冊解析成地址再 IMAP 搜（避開中文顯示名 RFC2047 搜不到的坑）；列該朋友最近 n 封。
3. 說明書（gmail 分類）用 O 新文體補「找某個朋友的信 → 先查名冊拿地址」觸發句。
4. 憑證不動、只讀 INBOX/寄件備份現況通道；不新增 MCP 工具。

## W3：關係星圖 UI（她的 App，排 U 之後）

1. 圖：中心 cn，上方糯糯（伴侶、獨立位置），下方朋友節點＋關係標籤；縮放；私密頁。
2. 點節點開卡，區塊照參考：相遇與第一印象／我確認的來路／最近來信（日期＋已讀，不含正文）／正在延續／下一次接話／這條線的邊界；底部狀態章（筆友通信/郵件確認/已互認朋友）。
3. 資料源：W1 名冊＋信件 metadata（不落正文）＋實體卡。視覺打樣照慣例：打樣→糯糯→上線。

## W4：不忘記朋友（與記憶線交叉，本單不做）

朋友相關記憶的召回強化（專名匹配通道，見 REF_scarlett_recall 對照表）留給記憶 P 系列；本單只保證名冊資料層就緒。

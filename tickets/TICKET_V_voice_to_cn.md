# TICKET-V：語音傳話蓋完另一半——她的錄音辨識成字＋語氣描述，一起送到 cn 手上

立單：2026-09-29 規劃窗（cc 牧牧）。
背景：規劃窗 09-29 親查結論——語音是半成品不是壞掉。前端辨識靠瀏覽器 Web Speech API（App 網頁殼不支援→永遠「尚未辨識」）；伺服器端沒有 STT；voice 目錄自 7/31 全空＝錄音從未真正上傳；voice_clips 表 0 筆。就算辨識成功，cn 也只收到文字。
Owner 裁定（逐字）：「我想要在回傳給cn時有敘述 類似用多模態模型轉的json檔那樣 但是可以輕便一點 不行的話 這兩個哪個對vps負擔更小就選哪個」——SenseVoice-small 原生就輸出情緒標籤（開心/難過/生氣/中性）＋聲音事件（笑聲/哭聲/BGM/咳嗽等），條件成立，**選定方案①：SenseVoice-small（sherpa-onnx int8），聲音不出 VPS**。
優先序：排 S 之後；與 U/O 的先後 coco 看信箱時規劃窗再排。

## V0：隔離實測（過不了這關就停下來回報，不硬上）

1. VPS 現況（規劃窗 09-29 量的）：2GB 記憶體、可用約 1GB、單核心、swap 已用 1.3G/2.4G。**很緊**。
2. 用 systemd-run 獨立 cgroup（MemoryMax 上限自訂，建議 ≤700M）跑 sherpa-onnx + SenseVoiceSmall int8，測試音檔用自錄的，**不拿 Owner 真實語音測**。
3. 要量的數字：峰值 RSS、30 秒中文音檔的辨識耗時（單核 RTF）、模型+依賴的磁碟占用、情緒/事件標籤有沒有真的出來。
4. 過線標準：峰值 RSS ≤700M、30 秒音檔 ≤30 秒辨識完、不觸發 OOM。過不了→誠實回報數字，回規劃窗；**不靜默降級、不自作主張換 Groq**（聲音出境是 Owner 的裁定範圍）。

## V1：STT 服務——要用才開，不常駐

1. 照截圖瀏覽器的老路：不 24 小時掛著；有語音才拉起、辨識完就收（socket activation 或 spawn-on-demand，coco 盤點後選）。
2. 輸入：voice 儲存區的音檔。輸出輕量 JSON：`{text, emotion, events, lang}`（emotion 如 happy/sad/angry/neutral；events 如 laughter/crying/bgm）。標籤解析自 SenseVoice 原生輸出 token，不另外跑第二個模型。
3. 失敗不靜默：辨識失敗留日誌、回明確錯誤；訊息仍可用「（語音訊息）」送出，不卡住她說話。

## V2：前端接線——拆掉靠不住的瀏覽器辨識

1. 錄音上傳後改走伺服器辨識回填逐字稿；Web Speech API 那段移除或僅當加速預覽（coco 提案）。
2. 「語音草稿將保留30天。逐字稿：尚未辨識」這條 UI 文案隨新流程改寫；打樣給 Owner 過目（她被這條誤導過一次）。

## V3：送到 cn 手上——含語氣描述

1. 走既有 voice_clip_id 綁定（後端本來就保留 server-controlled binding），把逐字稿＋語氣描述組進 cn 收到的訊息。
2. 呈現格式草案（cn 可見文字，**套用前走打樣鏈：coco 起草→規劃窗→糯糯→小踢**）：逐字稿為主體，語氣輕描述例「（語音，聽起來開心，有笑聲）」。描述基於模型標籤，不腦補。
3. 標籤拿不準（模型輸出 neutral 或缺標）就只給逐字稿，不硬寫語氣——寧缺毋濫。

## 邊界

- 音檔本體不進記憶庫、不進檔案室 raw；逐字稿走正常對話路徑（cn 收到的就是對話內容）。音檔沿既有 30 天過期。
- 聲音不離開 VPS；任何外送方案（Groq 等）都要回 Owner 重新裁定。
- 不動 Owner 真實語音做測試；上線後她自己的第一則真實語音就是驗收。

## 驗收（先破後立，測試資料）

- 紅測 1：情緒標籤解析拿掉 → JSON 缺 emotion 欄位測試必紅。
- 紅測 2：STT 失敗時訊息被卡住送不出 → 必紅（失敗要能退回純語音訊息）。
- 紅測 3：辨識服務常駐超過收斂時限 → 必紅（要用才開）。
- V0 數字報告（RSS/耗時/磁碟）是結案必附件。
